工作原理 · 三级加载

像操作系统启动一样，逐级加载规范

借鉴计算机从固件到内核的链式启动思路：入口层只做最小引导，把复杂度留给下一层。每一层只做一件事。

1
入口层 · 一行引导代码
项目根目录的 CLAUDE.md / .cursorrules，只做一件事：告诉 AI 去哪里找规范引擎。
~1 行
▼ 自动加载
2
路由引擎 · 读懂你的项目
读取项目自述卡（记录用什么架构、什么技术栈）→ 匹配架构类型 → 决定加载哪些规范。
SKILL.md
▼ 按需加载
3
规范库 · 只在需要时出现
通用规范（始终加载）+ 架构方案（按类型选一）+ 领域插件（按需激活），不会一次性塞满上下文。

规范架构 · 三层模型

从底线规则到领域专长，热插拔组合

三层分离，借鉴插件化思想：底层是稳定的地基，中层是可替换的模块，顶层是可添加的能力。团队只激活自己需要的部分。

      读到这里，几个名词先对齐一下

      项目指纹 = 项目自述卡，记录用什么架构、什么技术栈、属于哪些业务领域。
      领域插件 (SPI) = 某个业务领域的专属规则包，需要时挂载，不需要时忽略。
      标准体系管理委员会 = 负责规范评审与变更把关的团队，决定规则能否合并生效。

      路由引擎 · 九阶段
      
      AI 每次写代码，九步默默完成
      
      
      引擎不会一次性把所有规范塞进上下文。它先建索引，再按当前任务按需深入加载 · 实测单次任务通常只加载 2~4 份完整规范。

      长效机制 · 迭代管理
      
      规范不能想改就改，但可以安全演进
      
      
      所有变更必须走「提案 → 评审 → 自动校验 → 合并」流程，由标准体系管理委员会把关。这套机制保证规范在长期迭代中不会退化。
