# 规范体系优化计划与外部技能包边界界定指南

> 版本: 1.0 | 日期: 2026-06-18 | 状态: 待评估

---

## 一、定位差异矩阵

本节明确界定"企业编码规范体系"（以下简称**规范体系**）与外部技能包（Superpowers、GStack、CodeGraph、OpenWolf 等）的本质区别，防止概念混淆和功能越界。

### 1.1 核心定位对比

| 维度 | 规范体系 (spec-engine) | 外部技能包 |
|------|----------------------|-----------|
| **本质** | 编码规则的知识运行时 — 告诉 AI "代码应该遵循什么标准" | 能力增强中间件 — 给 AI 增加额外的工具和行为 |
| **产出物** | 约束性规则文档（MUST/SHOULD/MAY 级别） | 可执行的工具链（浏览器、终端、文件操作等） |
| **加载时机** | 编码任务启动前，由 SKILL.md 引擎按指纹路由加载 | 运行时按需调用，通常由用户指令或 AI 判断触发 |
| **影响范围** | 仅影响代码生成的内容（命名、结构、模式、风格） | 影响 AI 的行为能力边界（能做什么、怎么操作） |
| **可替代性** | 不可被外部技能包替代 — 规则是企业独有的 | 可独立运行，不依赖特定规范体系 |
| **版本管理** | 体系内 SemVer，registry.yaml 统一调度 | 各自独立版本，npm/pip 等包管理器管理 |

### 1.2 逐项差异矩阵

| 对比项 | 规范体系 | Superpowers | GStack | CodeGraph | OpenWolf |
|--------|---------|-------------|--------|-----------|----------|
| 设计目标 | 确保 AI 输出代码符合企业编码标准 | 增强 AI 编程助手的综合能力 | 提供浏览器自动化、设计审查、性能基准等开发工具 | 代码结构可视化与依赖分析 | 为 AI 提供项目记忆和学习能力 |
| 核心能力 | 规范路由 + 规则注入 + 变更边界控制 | 代码生成增强 + 多模型协同 | 浏览器控制 + UI 测试 + 设计 QA | 依赖图谱 + 架构可视化 | 跨会话记忆 + token 追踪 |
| 输入 | spec-manifest.yaml + routing-rules.yaml | 用户指令 + 项目代码 | URL + 截图 + DOM | 项目源码 | 会话历史 + 项目文件 |
| 输出 | 约束性规则（代码应如何写） | 增强后的代码生成行为 | 测试报告 + 截图 + 性能数据 | 依赖关系图 + 架构分析报告 | 持久化记忆 + 学习笔记 |
| 调用方式 | 由 SKILL.md 引擎自动加载，无需用户干预 | 用户在会话中主动调用 | 用户通过 /browse, /benchmark 等命令调用 | 用户通过 codegraph 命令调用 | openwolf init 后自动运行 |
| 是否修改代码 | 不直接修改，通过规则约束 AI 的代码生成 | 直接参与代码生成过程 | 不修改代码，提供测试和审查能力 | 不修改代码，提供分析能力 | 不修改代码，提供记忆能力 |
| 企业定制性 | 高 — 规则内容完全由企业定义 | 低 — 通用能力包 | 低 — 通用工具集 | 低 — 通用分析工具 | 低 — 通用记忆框架 |
| 与规范体系的关系 | — | 平行共存，不互相依赖 | 平行共存，不互相依赖 | 可被规范体系引用为分析手段 | 可增强规范体系的学习效果 |

### 1.3 边界红线（不可逾越）

以下行为被定义为"越界"，在任何情况下禁止发生：

**红线 1：规范体系不得调用外部技能包的执行逻辑。**
规范体系的文件（SKILL.md、routing-rules.yaml、所有 .md 规范文件）中不得出现对外部技能包命令的调用指令。

正例：`规范规则 PROF-FE-203 要求使用 Pinia defineStore 定义状态管理。` — 这是纯规则声明。

反例：`规范规则 PROF-FE-203 要求运行 superpowers analyze-state 来验证状态管理方案。` — 这越界调用了外部技能包。

**红线 2：外部技能包不得修改规范体系的内容文件。**
任何外部技能包的执行流程中不得写入或修改 docs/ 目录下的任何 .md、.yaml 文件。

正例：`CodeGraph 分析项目依赖后，开发者手动决定是否调整规范配置。` — 人做决策。

反例：`CodeGraph 分析后自动修改 routing-rules.yaml 中的包依赖关系。` — 工具篡改规范。

**红线 3：bootstrap.sh 的推荐增强区仅做信息展示，不执行安装。**
推荐增强工具（OpenWolf、CodeGraph、Superpowers、gstack）仅显示安装指引，bootstrap.sh 不自动安装或初始化任何外部工具。

正例：`echo "如需安装: npm install -g openwolf"` — 仅提供信息。

反例：`npm install -g openwolf && openwolf init` — 自动执行安装。

## 二、调用链隔离规则

### 2.1 三层调用链模型

规范体系的运行时调用链分为三层，每层有不同的隔离要求：

```
┌────────────────────────────────────────────────────────────────┐
│  Layer A: 规范加载层（Spec Loading）                             │
│  ─────────────────────────────────────────────────────────     │
│  SKILL.md → manifest → routing-rules → 规范文件                 │
│  隔离级别: 封闭                                                 │
│  规则: 禁止引入任何外部技能包。仅读取 docs/ 和 .spec/ 下文件。     │
├────────────────────────────────────────────────────────────────┤
│  Layer B: 代码生成层（Code Generation）                          │
│  ─────────────────────────────────────────────────────────     │
│  AI 根据加载的规范生成代码                                        │
│  隔离级别: 半开放                                               │
│  规则: 代码生成受规范约束，但 AI 可同时使用外部工具辅助开发。       │
│        规范要求 MUST 优先于外部工具的默认行为。                    │
├────────────────────────────────────────────────────────────────┤
│  Layer C: 开发辅助层（Dev Assistance）                           │
│  ─────────────────────────────────────────────────────────     │
│  OpenWolf 记忆 / CodeGraph 分析 / GStack 测试                   │
│  隔离级别: 开放                                                 │
│  规则: 外部工具自由运行，但不得修改规范体系的文件。                 │
│        外部工具的分析结果可作为开发者决策参考，不自动注入规范。      │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 各层隔离规则详表

| 规则编号 | 所属层 | 规则内容 | 违反后果 |
|---------|--------|---------|---------|
| ISO-001 | A | SKILL.md 的 9 阶段流程中不得调用 `superpowers`、`gstack`、`codegraph`、`openwolf` 等外部命令 | 规范引擎被污染，加载结果不可信 |
| ISO-002 | A | routing-rules.yaml 的 keywords 和 match 规则不得引用外部技能包的输出格式 | 路由匹配依赖外部状态，破坏独立性 |
| ISO-003 | A | 规范 .md 文件中的"验证方式"章节仅可引用 validate-spec.sh，不得引用外部工具的检测命令 | 验证链路断裂 |
| ISO-004 | B | 当规范规则与外部工具默认行为冲突时，规范 MUST 优先 | 代码不符合企业标准 |
| ISO-005 | B | AI 生成代码时可参考 CodeGraph 的依赖分析结果，但规范规则本身不得依赖该结果 | 规范的可移植性受损 |
| ISO-006 | C | 外部工具不得写入 docs/、.spec/ 目录下的任何文件 | 规范内容被篡改 |
| ISO-007 | C | OpenWolf 的 cerebrum.md 中可记录"遵循了哪些规范"的学习笔记，但不得重写规范规则 | 规范权威性被削弱 |

### 2.3 组合使用策略

规范体系与外部工具可以协同工作，但遵循以下组合原则：

**原则 1：规范驱动，工具辅助。**
规范定义"该怎么做"，外部工具帮助"做得更好"。决策权始终在规范和开发者手中。

示例：规范要求 Controller 层不得直接调用 Repository。CodeGraph 可以生成依赖图来验证当前项目是否违反，但 CodeGraph 的分析结果不改变规范规则本身。

**原则 2：规范独立可运行。**
移除所有外部工具后，规范体系仍能完整运行（SKILL.md 加载 → 路由匹配 → 规则注入 → 代码生成）。外部工具是锦上添花，不是必要条件。

示例：OpenWolf 未安装时，bootstrap.sh 跳过推荐区域，规范引擎正常完成 5 步注入流程。

**原则 3：外部工具的输出不进入规范路由。**
外部工具的分析结果不得被 routing-rules.yaml 作为匹配条件，也不得被 SKILL.md 作为规范加载的触发条件。

示例：不可以写"如果 CodeGraph 检测到循环依赖，则自动加载 resilience 包"。应改为"开发者根据 CodeGraph 报告，手动在 manifest 中添加 resilience 到 profiles 列表"。

### 2.4 bootstrap.sh 推荐增强的设计规范

bootstrap.sh 的"推荐增强"区域遵循严格的展示规范：

```
检测到工具已安装 → 显示"推荐增强"（cyan），建议在本项目中初始化
检测到工具未安装 → 显示"可选增强"（yellow），提供安装命令
检测到项目已配置 → 显示 info 提示，跳过推荐
```

所有推荐均为纯信息输出，不执行任何安装或配置命令。开发者自行决定是否引入。

当前推荐增强工具清单：

| 工具 | 检测命令 | 互补价值 | 与规范的隔离点 |
|------|---------|---------|--------------|
| OpenWolf | `command -v openwolf` | 跨会话记忆，避免重复犯错 | 记忆内容不进入规范路由 |
| CodeGraph | `command -v codegraph` | 依赖可视化，辅助架构决策 | 分析结果不修改 routing-rules |
| Superpowers | `command -v superpowers` | AI 编程能力增强 | 增强行为不覆盖规范规则 |
| gstack | `command -v gstack` | 浏览器自动化、设计审查 | 测试结果不注入规范上下文 |

## 三、组合使用策略

### 3.1 典型协同场景

**场景 A：新项目接入 + 架构分析**
1. 运行 `bootstrap.sh` 完成规范注入
2. 运行 `codegraph analyze` 生成依赖图谱
3. 开发者参考图谱决定 profiles 组合
4. 手动更新 `spec-manifest.yaml`

规范体系在步骤 1 完成注入，步骤 2-4 是开发者借助外部工具做决策，规范不感知也不依赖。

**场景 B：编码过程中的质量保障**
1. AI 按规范生成代码（Layer A+B 运行）
2. 开发者用 GStack `/browse` 做 UI 测试（Layer C 运行）
3. 发现 UI 问题后，开发者指导 AI 修改代码
4. AI 修改时仍受规范约束（如 component.md 的 PROF-FE-102）

GStack 提供了发现问题的能力，规范提供了修复问题的标准。两者正交。

**场景 C：跨会话的规范学习**
1. 第一次会话中 AI 遵循规范生成代码
2. OpenWolf 记录"本项目使用 arch-ddd + persistence-mybatis-plus"
3. 第二次会话中 OpenWolf 提供记忆上下文
4. SKILL.md 独立重新加载规范（不依赖 OpenWolf 的记忆）

OpenWolf 加速了上下文恢复，但 SKILL.md 的 9 阶段流程独立完整执行。

### 3.2 反模式清单

| 反模式 | 描述 | 正确做法 |
|--------|------|---------|
| 规范依赖外部分析 | routing-rules 根据 CodeGraph 输出自动选择 profiles | 开发者手动在 manifest 中声明 profiles |
| 外部工具覆写规范 | Superpowers 的代码生成模板覆盖规范规则 | 规范要求 MUST 优先，Superpowers 模板适配规范 |
| 混合初始化 | bootstrap.sh 同时初始化规范引擎和外部工具 | bootstrap.sh 仅负责规范注入，外部工具各自初始化 |
| 记忆替代加载 | 依赖 OpenWolf 记忆而不执行 SKILL.md 加载流程 | 每次会话 SKILL.md 必须完整执行 9 阶段 |

## 四、细粒度优化任务拆解表

以下任务按优先级分为三档：

- **P0**：高投入产出比，与现有架构正交性强，建议立即启动
- **P1**：中等优先级，依赖 P0 或需要一定前置准备
- **P2**：远期规划，可在体系经过实际项目验证后推进

### C. 规范体系 vs 外部工具：快速判定表

当不确定某项功能应该放在规范体系还是外部工具时，使用以下判定表：

| 判定问题 | 回答"是" | 回答"否" |
|---------|---------|---------|
| 它定义的是"代码应该怎么写"吗？ | → 属于规范体系 | → 继续判断 |
| 它需要访问外部系统（浏览器、网络、API）吗？ | → 属于外部工具 | → 继续判断 |
| 它的输出是约束性规则吗？ | → 属于规范体系 | → 属于外部工具 |
| 没有它，AI 仍然能生成代码（只是可能不符合标准）吗？ | → 属于规范体系 | → 属于外部工具 |
| 它是企业独有的、不可被通用工具替代的吗？ | → 属于规范体系 | → 属于外部工具 |
