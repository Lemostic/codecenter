## 一、需求梳理为什么至关重要

AI 辅助开发时代，需求梳理的重要性进一步放大：

| 维度 | 传统开发 | AI 辅助开发 |
|------|----------|-------------|
| 返工成本 | 中等 | **极高**（AI 生成的代码量大） |
| 理解偏差 | 需要人工沟通 | AI 可能产生幻觉 |
| 修改难度 | 代码量小 | 代码量大，改动复杂 |

需求不清的典型后果：

```
┌──────────────────────────────────────────────────────────┐
│ 需求不清 → AI 误解 → 大量代码 → 发现问题 → 重新开始    │
│                    ↑                                    │
│              浪费的时间和资源                           │
└──────────────────────────────────────────────────────────┘
```

需求梳理的 4 个核心目标：**消除歧义** / **明确边界** / **识别风险** / **建立共识**。

## 二、brainstorming 技能工作流

### 2.1 触发方式

```
用 brainstorming 模式，分析 [具体需求]
```

或：

```
请用 brainstorming 的方式分析这个需求
```

### 2.2 工作流程

```
┌─────────────┐
│ 用户提出需求  │
└──────┬──────┘
       ↓
┌──────▼──────┐
│ AI 追问澄清  │
└──────┬──────┘
       ↓
┌──────▼──────┐
│ 用户回答确认  │
└──────┬──────┘
       ↓
┌──────▼──────┐
│ 输出设计规范  │
└──────┬──────┘
       ↓
┌──────▼──────┐
│ 双方确认签字  │
└─────────────┘
```

### 2.3 典型问题清单（3 类）

| 类别 | 问题 | 目的 | 示例 |
|------|------|------|------|
| **需求澄清** | 真正的问题是什么 | 理解核心诉求 | "你真正想解决什么问题？" |
| | 用户是谁 | 明确目标群体 | "预期的用户是谁？" |
| | 成功的标准 | 定义成功 | "如何定义成功？" |
| | 约束条件 | 了解限制 | "有哪些约束条件？" |
| **功能边界** | 必须包含什么 | 明确核心功能 | "这个功能必须包含哪些部分？" |
| | 不包含什么 | 界定范围 | "哪些不在这次范围内？" |
| | 替代方案 | 寻找更优解 | "有没有更简单的方案？" |
| | 优先级 | 确定重点 | "核心功能和扩展功能分别是什么？" |
| **技术实现** | 技术栈要求 | 确定技术选型 | "有特定的技术要求吗？" |
| | 集成需求 | 了解外部依赖 | "需要和哪些系统对接？" |
| | 性能要求 | 确定非功能需求 | "响应时间/并发量要求是多少？" |
| | 安全要求 | 确定安全需求 | "有哪些安全相关的考虑？" |

**REQ-001** 在启动 AI 编码前 MUST 跑完 brainstorming 三类问题清单（需求澄清 / 功能边界 / 技术实现）。 [MUST]

## 三、DESIGN.md 编写规范

### 3.1 为什么需要 DESIGN.md

AI 编程时常见的设计偏差：

| AI 觉得好看的 | 实际项目需要的 |
|---------------|---------------|
| 按钮高度 48px | 按钮高度 32px |
| 圆角 16px | 圆角 6px |
| 卡片间距 32px | 卡片间距 16px |
| 页面内边距 60px | 页面内边距 24px |
| 各种阴影+渐变 | 简单的边框线 |

**DESIGN.md 的目标**：把项目的设计决策固化下来，让 AI 编码时直接遵循而非自由发挥。

### 3.2 DESIGN.md 模板结构

```yaml
---
version: "1.0"
name: "项目名称"
description: "项目风格描述"

# 颜色系统
colors:
  primary: "#1E3A5F"      # 主色，用于主要按钮、导航
  primary-hover: "#2D4A6F"
  accent: "#1677ff"        # 强调色，用于链接、重点信息
  background: "#F1F5F9"   # 页面背景
  text-primary: "#1E293B"   # 主要文本
  text-secondary: "#64748B"  # 次要文本
  border: "#E2E8F0"
  danger: "#DC2626"
  success: "#16A34A"
  warning: "#D97706"

# 字体系统
typography:
  font-family: "'PingFang SC', 'Microsoft YaHei', -apple-system, sans-serif"
  font-size-base: "14px"
  line-height-base: "1.5"

# 间距系统（基于 4px）
spacing:
  unit: "4px"
  1: "4px"
  2: "8px"
  3: "12px"
  4: "16px"
  6: "24px"
  8: "32px"

# 圆角
border-radius:
  sm: "4px"
  md: "6px"   # 默认圆角
  lg: "8px"

# 阴影
shadows:
  sm: "0 1px 2px 0 rgba(0, 0, 0, 0.05)"
  md: "0 4px 6px -1px rgba(0, 0, 0, 0.1)"
```

### 3.3 配套设计说明部分

```markdown
## 整体风格
- 简洁实用，不花哨
- 配色稳重，以深蓝为主色调
- 强调信息密度和操作效率

## 不适用的风格
- 不要用渐变背景
- 不要用大圆角（6px 封顶）
- 不要加不必要的动画

## 组件尺寸规范
| 组件 | 尺寸 | 说明 |
|------|------|------|
| 主按钮高度 | 32px | 主要操作按钮 |
| 输入框高度 | 32px | 标准输入框 |
| 表格行高 | 48px | 表格数据行 |
| 页面边距 | 24px | 页面内边距 |
| 卡片内边距 | 16px | 卡片内边距 |

## 禁止事项
1. 禁止在表格中使用卡片布局
2. 禁止使用超过 2 级的弹窗嵌套
3. 禁止使用超过 3 种主色调
```

**REQ-002** AI 编码 MUST 先读取项目 `DESIGN.md` 并严格遵守其中的颜色、字体、间距、圆角规范。 [MUST]

**REQ-003** DESIGN.md 中"禁止事项"清单 MUST 显式列出项目特有的反模式（如"不要渐变"），AI 编码时 MUST 避免触发。 [MUST]

### 3.4 从现有项目提取 DESIGN.md

**最值得看的文件**：
- `variables.css` / `theme.css` — 设计变量
- 项目的全局样式文件
- 现有组件的 CSS（Button / Input / Table）

**分段提取的 Prompt 模板**：

```
请分析以下样式文件，列出所有颜色值和它们的用途。

[粘贴 CSS 变量或组件样式]

输出格式：
- 主色: #xxxxxx → 用于...
- 成功色: #xxxxxx → 用于...
- 边框色: #xxxxxx → 用于...
```

## 四、需求分析的 5 个维度

```
         ┌─────────────┐
         │   用户是谁   │
         └──────┬──────┘
                │
    ┌───────────┼───────────┐
    ↓           ↓           ↓
┌───────┐  ┌───────┐  ┌───────┐
│做什么 │  │怎么做 │  │做到什么程度│
└───────┘  └───────┘  └───────┘
```

| 维度 | 内容 |
|------|------|
| 用户是谁 | 目标用户画像、使用场景、用户能力水平 |
| 做什么 | 核心功能、扩展功能、优先级排序 |
| 怎么做 | 技术选型、集成需求、约束条件 |
| 做到什么程度 | 性能要求、安全要求、可用性要求 |
| 验收标准 | 功能验收、质量验收、性能验收 |

## 六、常见问题与解决方案

### Q1: 用户说不清楚需求怎么办？

**解决方案**：
1. 提供竞品参考，让用户选择
2. 使用渐进式提问，先问最核心的问题
3. 提供选项让用户选择，而不是开放式回答
4. 从现有系统或功能类比

### Q2: 用户需求变化太快怎么办？

**解决方案**：
1. 明确 MVP 范围，先做核心功能
2. 建立需求变更流程，记录变更原因
3. 使用迭代开发，每次只实现已确认的需求
4. 设置需求冻结节点

### Q3: 多个相关方需求冲突怎么办？

**解决方案**：
1. 明确决策人和最终拍板权
2. 记录各方需求和理由
3. 评估需求的价值和成本
4. 组织专题讨论达成共识

### Q4: AI 理解的需求和实际需求有偏差怎么办？

**解决方案**：
1. 使用 AI 输出需求文档，人工复核
2. 使用原型或草图辅助沟通
3. 分阶段确认，每阶段结束都确认
4. 提供正面和反面示例帮助 AI 理解
