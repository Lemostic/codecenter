# 概要设计自检指南（灵魂5问 + 范式检查 + POC验证）

> 本指南帮助你在概要设计评审前完成系统自检，确保设计经得起追问。核心理念：**业务场景在前，技术组件在后。**

---

## 核心范式：场景驱动设计

**业务场景在前，技术组件在后。**

传统设计评审中，最常见的失败模式是"组件驱动设计"——开篇就讲用了什么框架、什么中间件，却说不清楚业务到底卡在哪里。场景驱动设计要求你反过来思考：先说清楚业务场景和卡点，再推导策略，最后才选工具。

**铁律：P0没过，绝不进入P1。** 没有诊断就没有方向，没有方向一切白搭。

**核心句式**（四个词一个都不能少，顺序一个都不能乱）：

> **业务场景 -> 卡点 -> 策略 -> 工具**

任何设计文档，如果不能用这一句话讲清楚，说明设计者自己还没想明白。

---

## 设计优先级（5层级）

| 优先级 | 关注点 | 一句话定义 | 跑偏代价 |
|--------|--------|-----------|---------|
| **P0** 问题诊断 | 慢在哪一行、哪个SQL、哪段规则 | 没有诊断就没有方向 | 整个设计建立在假设之上 |
| **P1** 业务场景 | 数据长什么样、规则长什么样、卡点长什么样 | 场景没想清，组件白搭 | 做出来的东西解决不了真实问题 |
| **P2** 策略选型 | 临时表vs流式、SQL校验vs应用层校验 | 策略错了，工具再好也白搭 | 返工重来 |
| **P3** 工具/组件 | Spring Batch、EasyExcel等 | 工具是手段，不是目标 | 过度设计，引入不必要的复杂度 |
| **P4** 实现细节 | 参数、配置、代码、API | 最后一步 | 本末倒置 |

**铁律：**

- **P0没说清楚，禁止进入P1** -- 连问题在哪都不知道，谈什么业务场景？
- **P1没说清楚，禁止进入P2~P4** -- 场景模糊，策略和工具就是空中楼阁。
- **P3的内容占比，不应超过P0+P1+P2的总和** -- 工具讲太多，说明场景没想透。

## 灵魂5问自检

### 问1：你的"性能问题"是"症状"还是"诊断"？

| 症状（模糊） | 诊断（精确） |
|-------------|-------------|
| "导入很慢" | "10万行Excel解析耗时45s，瓶颈在POI全量加载DOM，占82%" |
| "校验性能差" | "50条规则串行执行，第12条正则规则占60%耗时" |
| "数据库扛不住" | "单条INSERT 3ms，但循环10万次，总计30s，瓶颈在逐行提交" |

**通过条件：** 有profiling数据，给出瓶颈占比（如"X环节占总耗时Y%"）。没有数据就是猜，猜就不是诊断。

---

### 问2：你的瓶颈在"通用层"还是"业务层"？

| 通用层（框架能帮） | 业务层（框架帮不上） |
|-------------------|-------------------|
| 文件解析OOM -> 流式解析 | 复杂校验规则的执行顺序与短路策略 |
| 逐行提交慢 -> 批量提交 | 字段间的联动校验逻辑 |
| 单线程处理 -> 分片并行 | 业务数据的分片策略设计 |
| 重复查询 -> 缓存 | 规则引擎的编排与结果复用 |

**通过条件：** 瓶颈分类完成。通用层瓶颈可用工具解决；业务层瓶颈必须有业务策略，框架帮不了你。

---

### 问3：你的性能提升，是"组件升级"还是"策略优化"？

| 优化类型 | 典型提升幅度 | 示例 |
|---------|------------|------|
| **组件升级** | 1.2x ~ 2x | POI换EasyExcel、单条改批量 |
| **策略优化** | 10x ~ 100x | 全量加载改流式、串行改并行、逐行改分片 |
| **业务优化** | 100x ~ 1000x | 砍掉不必要的校验、合并重复流程、异步化非关键路径 |

**通过条件：** 每一条性能数字都绑定了具体的优化策略。"提升了10倍"但说不清楚哪个策略贡献的，不通过。

---

### 问4：你的设计是"自下而上"还是"自上而下"？

**自下而上（典型错误模式）：**

```
第1页：我们用了Spring Batch
第2页：配置了这些Step和Job
第3页：性能测试数据
第4页：哦对了，业务场景是...
```

**自上而下（正确模式）：**

```
第1页：业务场景与痛点
第2页：诊断数据与瓶颈分析
第3页：针对每个瓶颈的策略
第4页：工具选型与落地（占比<30%）
```

**通过条件：** 设计文档第一页是业务场景，工具/组件相关内容占比 < 30%。

---

### 问5：你的POC验证，验证的是"技术能用"还是"业务能跑"？

| 技术能用（最低标准） | 业务能跑（真实验证） |
|-------------------|-------------------|
| Demo数据跑通 | 真实业务数据跑通 |
| Happy Path验证 | 覆盖80%复杂度的边界场景 |
| "框架能集成" | "真实规则+真实数据下性能达标" |
| 无异常=通过 | 异常场景有兜底策略 |

**通过条件：** POC范围明确，用真实数据跑过核心场景，性能数字有实测支撑而非估算。

## 范式检查方法

设计文档写完后，用以下方法自检：

**第一步：把每个章节归类到P0~P4**

逐段审视你的设计文档，给每个章节/段落打上P0~P4的标签。

**第二步：统计占比**

按页数或段落数统计各优先级的占比。

**第三步：判定**

| P3（工具/组件）占比 | 判定 | 行动 |
|-------------------|------|------|
| <= 30% | PASS | 结构健康 |
| 30% ~ 50% | WARNING | 压缩工具篇幅，补充场景和策略 |
| > 50% | FAIL | 需要重写，从业务场景重新出发 |

## 场景驱动叙事模板

按以下四段式组织你的设计文档或评审演讲：

**1. 业务场景与痛点（开场）**
> "我们的{{business_scenario}}场景，面临{{pain_point}}的问题。"

**2. 业务卡点（含profiling数据）**
> "经过诊断，瓶颈在{{bottleneck_location}}，占总耗时{{percentage}}%。"

**3. 优化策略（按卡点一一对应）**
> "针对卡点A，策略是{{strategy_a}}；针对卡点B，策略是{{strategy_b}}。"

**4. 工具落地（占比 < 30%）**
> "基于以上策略，选用{{tool}}来实现，落地方式是{{implementation}}。"

### 电梯演讲模板

用一句话讲清楚你的设计（30秒内）：

> "我们的业务场景是**{{X}}**，卡点是**{{Y}}**，策略是**{{Z}}**，工具是**{{W}}**。"

如果填不出来，说明还没想清楚。

## 评委6轮追问准备

评审会上，评委通常按以下6轮递进追问。提前准备好每一轮的回答：

| 轮次 | 追问方向 | 典型问题 | 准备要点 |
|------|---------|---------|---------|
| R1 诊断 | 原来慢在哪？ | "profiling数据呢？瓶颈占比？" | 准备好火焰图/耗时分布表 |
| R2 分类 | 通用层还是业务层？ | "哪些瓶颈工具能解决，哪些不能？" | 列出瓶颈分类表 |
| R3 数字 | 性能数字哪来的？ | "10倍提升是怎么算的？" | 每个数字绑定具体策略和实测数据 |
| R4 价值 | 不用这个工具会怎样？ | "Spring Batch的不可替代性在哪？" | 说清楚工具解决的是通用层问题还是业务层问题 |
| R5 POC | 真实数据跑过吗？ | "POC覆盖了多少业务复杂度？" | POC范围清单 + 真实数据测试结果 |
| R6 适配 | 特殊字段/规则能扛住吗？ | "如果字段类型变了怎么办？" | 边界场景分析 + 扩展性设计 |

**应对原则：** 每一轮回答都要回到"业务场景 -> 卡点 -> 策略 -> 工具"的句式。被问住不丢人，说不清场景才丢人。

## POC验证4原则

1. **验证业务能跑，而非技术能用** -- Demo跑通只是最低标准，不是验收标准。
2. **用真实数据，不用mock数据** -- mock数据永远比真实数据"干净"，掩盖了80%的真实问题。
3. **覆盖核心业务的80%复杂度** -- Happy Path只是20%的复杂度，边界场景才是真考验。
4. **性能数字必须有实测数据支撑** -- "预估"和"理论上"不算数。

### POC范围检查清单

- [ ] 使用了生产环境的真实数据集（或等比例脱敏数据）
- [ ] 覆盖了核心业务场景的主流程
- [ ] 覆盖了至少3种边界/异常场景
- [ ] 性能测试在目标硬件/环境上执行
- [ ] 记录了每个测试场景的耗时数据
- [ ] 明确了POC未覆盖的场景及原因
- [ ] 性能基线已建立（优化前 vs 优化后）

## 常见误判（避坑指南）

| 误判 | 真相 |
|------|------|
| "用Spring Batch性能更好" | 默认单Chunk单线程，价值在通用能力封装（断点续跑、失败重试），不在性能 |
| "EasyExcel比POI快" | 价值是流式解析不OOM，单纯速度差异不大；真正的提速来自策略（分片、并行） |
| "用了Redis性能就上来了" | 解决的是远程IO延迟和热点数据缓存，解决不了业务规则计算和本地CPU瓶颈 |
| "切了微服务性能就好了" | 解决的是团队协作和独立扩展性，跟单机性能没有关系 |
| "多线程一定能加速" | 有锁竞争、上下文切换、线程池配置的代价；不分片的多线程可能是负优化 |
| "框架越新越牛" | 匹配业务场景最重要；新框架的学习成本和踩坑成本也是代价 |
| "性能提升是组件的功劳" | 真正提升几乎从来不是组件的功劳，是策略的功劳（流式、分片、并行、短路） |
| "POC跑通了=业务能用" | 跑通是最低标准，业务80%复杂度才是真考验 |

## 自检清单（每次设计前过一遍）

### P0 问题诊断

- [ ] 有明确的性能/瓶颈profiling数据
- [ ] 瓶颈定位到具体行/SQL/规则，而非模糊描述
- [ ] 每条瓶颈有占比数据（占总耗时/资源的百分比）

### P1 业务场景

- [ ] 能用一句话描述核心业务场景
- [ ] 数据规模、数据结构、业务规则都已梳理清楚
- [ ] 卡点已从业务视角描述（不是技术视角）

### P2 策略选型

- [ ] 每个卡点都有对应的优化策略
- [ ] 策略选择有理有据（为什么选A不选B）
- [ ] 性能数字绑定了具体策略，而非笼统归因

### P3 工具/组件

- [ ] 工具选型基于策略推导，而非经验惯性
- [ ] 工具内容占比 < 30%
- [ ] 能说清楚"不用这个工具会怎样"

### P4 实现细节

- [ ] API设计、参数配置、代码结构在P0~P3之后展开
- [ ] 实现细节不喧宾夺主

### 整体检查

- [ ] 设计文档第一页是业务场景，不是工具介绍
- [ ] 能用"业务场景->卡点->策略->工具"一句话讲清楚
- [ ] POC已用真实数据验证，覆盖80%业务复杂度
- [ ] 已准备好评委6轮追问的回答
