## 一、调试的核心原则

1. **复现优先于假设** — 没复现过的 bug 不能算"修好"
2. **证据优于直觉** — "我猜可能是 X"不是根因，"日志显示 X"才是
3. **改一行就验证一行** — 不要连续改 3 个变量再一起测
4. **保持变更可回滚** — 任何 fix 都必须能用 `git revert` 回退
5. **记录全过程** — 排查过程 = 团队知识资产，不是负担

---

## 二、4 阶段调试流程

### 阶段一：问题定义（必须填写）

**模板（问题定义）:**

```markdown
# 问题定义

### 现象描述
- [具体错误信息或表现]

### 影响范围
- [影响哪些功能/用户]

### 发现时间
- [什么时候发现的]

### 复现条件
- [在什么条件下可以复现]

### 严重程度
- [P0 / P1 / P2 / P3]
```

**严重程度分级:**

| 等级 | 标准 | 响应时间 |
|------|------|----------|
| P0 | 阻塞核心业务 / 数据丢失 / 安全漏洞 | 立即处理（< 1 小时） |
| P1 | 主要功能不可用 / 影响多数用户 | 当天处理（< 8 小时） |
| P2 | 次要功能受影响 / 有 workaround | 本周处理（< 3 天） |
| P3 | 边缘场景 / 体验问题 | 排期处理（< 2 周） |

**问题未定义清楚前禁止进入下一阶段。**

### 阶段二：信息收集（从轻量到重量）

收集顺序（成本递增）：

1. 错误日志 / 控制台输出
2. 用户报告的操作步骤
3. 最近代码变更（`git diff`）
4. 系统指标（CPU/内存/网络）
5. 数据库状态
6. 第三方服务状态
7. 生产环境日志

**信息收集检查清单:**

- [ ] 完整的错误堆栈
- [ ] 相关的业务日志
- [ ] 用户操作步骤
- [ ] 发生时间范围
- [ ] 最近部署/配置变更
- [ ] 相关系统的状态

**信息不完整时禁止跳到阶段三。**

### 阶段三：假设与验证

**假设记录模板:**

```typescript
interface HypothesisTest {
  id: string;                    // 假设编号，如 H1
  hypothesis: string;             // 假设内容
  probability: 'high' | 'medium' | 'low';  // 概率评估
  verificationSteps: string[];   // 验证步骤
  result: 'confirmed' | 'ruled_out' | 'inconclusive';
  evidence: string;               // 证据
  timestamp: Date;
}

// 使用示例
const hypothesisTests: HypothesisTest[] = [
  {
    id: 'H1',
    hypothesis: '数据库连接池耗尽',
    probability: 'high',
    verificationSteps: [
      '检查数据库连接数: SHOW STATUS LIKE "Threads_connected"',
      '检查连接池配置: 最大连接数 vs 实际使用',
      '检查是否有连接泄漏: 长时间运行的查询'
    ],
    result: 'confirmed',
    evidence: '连接数达到最大值 100，新请求被拒绝',
    timestamp: new Date()
  }
];
```

**假设验证原则:**

- 至少 2 个独立证据才能"确认"一个假设
- 1 个反例即可"排除"一个假设
- 不允许"看起来像"就跳到修复 — 必须验证
- 高风险操作（数据删除/结构变更）必须先备份再验证

### 阶段四：根因确认与修复

**根因确认标准（三条同时满足）:**

```
┌────────────────────────────────────────────────────────────┐
│  ✓ 能够解释所有观察到的现象                                  │
│  ✓ 可以通过人为引入相同条件复现问题                          │
│  ✓ 修复后问题不再出现                                      │
└────────────────────────────────────────────────────────────┘
```

**根因未确认前禁止修复（避免治标不治本）。**

## 三、常见问题模式

### 3.1 前端常见问题模式

| 问题模式 | 典型特征 | 排查方向 |
|----------|----------|----------|
| 白屏 | JS 错误/资源加载失败 | 检查控制台错误、网络请求 |
| 组件不渲染 | 条件渲染逻辑、props 问题 | 检查 React DevTools |
| API 请求失败 | CORS/网络/后端问题 | 检查 Network 面板 |
| 内存泄漏 | 页面越用越卡、定时器未清理 | 检查 DevTools Memory |

**白屏问题排查流程:**

```
1. 检查控制台是否有错误
   ↓
2. 检查 Network 面板资源加载
   ↓
3. 检查 React/Vue DevTools 组件树
   ↓
4. 检查是否有异步数据未加载
   ↓
5. 检查路由配置是否正确
```

### 3.2 后端常见问题模式

| 问题模式 | 典型特征 | 排查方向 |
|----------|----------|----------|
| 500 错误 | 未捕获异常 | 检查日志堆栈 |
| 超时 | 慢查询/外部依赖 | 检查链路追踪（traceId） |
| 内存溢出 | OOM/堆内存不足 | 检查堆快照 |
| 连接拒绝 | 服务宕机/端口不对 | 检查服务状态 |

**500 错误排查流程:**

```
1. 查找对应时间戳的错误日志
   ↓
2. 分析完整堆栈信息
   ↓
3. 如果是业务异常，检查业务逻辑
   ↓
4. 如果是系统异常，检查资源状况
   ↓
5. 确认是否是新变更引入
```

### 3.3 数据库常见问题模式

| 问题模式 | 典型特征 | 排查方向 |
|----------|----------|----------|
| 慢查询 | 响应时间 > 1s | 检查执行计划（EXPLAIN） |
| 连接超时 | 连接池耗尽 | 检查连接数配置 |
| 死锁 | 事务等待超时 | 检查锁等待链 |
| 数据不一致 | 并发写入问题 | 检查事务隔离级别 |

**慢查询排查流程:**

```
1. 开启慢查询日志或使用 APM
   ↓
2. 获取查询的执行计划 (EXPLAIN)
   ↓
3. 检查是否缺失索引
   ↓
4. 检查是否全表扫描
   ↓
5. 检查数据量是否超出预期
   ↓
6. 优化 SQL 或添加索引
   ↓
7. 重新评估性能
```

### 3.4 AI 辅助调试技巧

**使用 AI 调试的提问模板:**

```
模板 1：初步诊断
"出现 [现象描述]，错误信息是 [错误文本]，最近 24 小时变更 [git log 摘要]，请列出 3 个最可能的根因及验证方法。"

模板 2：原因分析
"基于上述诊断结果，对假设 H1 [假设内容]，列出 5 步验证方案，并标注每步需要哪些日志/工具/数据。"

模板 3：修复确认
"已应用 [修复内容]，请列出验证修复有效性的 3 个验证场景：单元测试 / 集成测试 / 灰度发布。"

模板 4：根因复盘
"问题已修复。本次根因是 [根因]。请输出一份 200 字以内的复盘报告，含：触发条件 / 检测延迟 / 防御措施。"
```

**AI 调试铁律:**

- AI 给出的每个"可能原因" MUST 标注证据来源（日志行号 / 监控指标 / 配置项）
- 不可"猜测式"建议修复方案
- 不可让 AI 自行修改生产环境配置（必须人工确认）
- 修复后 MUST 留观 24 小时，确认无回滚

## 四、调试的禁止事项

- ❌ 在生产环境直接调试（必须本地/测试环境复现）
- ❌ 仅凭"我猜可能是"就改代码
- ❌ 跳过问题定义直接看代码
- ❌ 修改代码后不验证就合并
- ❌ 把"无法复现"当"已修复"
- ❌ 用 print 调试代替日志系统
