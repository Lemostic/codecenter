## 主数据管理平台 — 前端设计方案

> 编辑日期：2026-06-15
> 基于 Turborepo + pnpm workspace 的 Monorepo 架构，包含 **mdm-model** 一个独立应用。

---

## 1. 方案概述

### 1.1 目标

采用 Turborepo 管理的 Monorepo 架构，构建可独立构建、独立部署的应用（mdm-model），同时抽取共享代码为内部包，消除重复、统一演进节奏。

### 1.2 技术选型

| 维度 | 选型 | 理由 |
| --- | --- | --- |
| Monorepo 编排 | **Turborepo** | 增量构建 + 任务依赖图 + 远端缓存，原生支持 Vite |
| 包管理器 | **pnpm** | workspace 协议 (`workspace:*`) 原生链接内部包，严格依赖隔离 |
| 构建工具 | Vite 5 | 每个 app 各自持有 `vite.config.ts`，共享预设于 `packages/config-vite` |
| 类型检查 | vue-tsc | 通过 Turborepo pipeline 在构建前统一执行 |
| 测试框架 | **Vitest 2** | 单元测试 + 组件测试，与 Vite 无缝集成，速度快，TypeScript 支持好 |
| 测试工具 | **@vue/test-utils** | Vue 3 组件测试工具 |
| DOM 模拟 | **happy-dom** | 轻量级 DOM 模拟，比 jsdom 更快 |

### 1.3 应用与包的划分

| 包名 | 目录 | 说明 |
| --- | --- | --- |
| `@mdm/model-app` | **apps/mdm-model** | 主数据模型管理应用（含模型列表、填报设计、属性配置、模型管理、质量规则、相似规则） |
| `@mdm/core` | **packages/mdm-core** | 框架基础设施（auth、http、i18n 引擎、router 引擎、layout、基础类型、平台配置加载） |
| `@mdm/common` | **packages/mdm-common** | 跨应用共享（Dm-* 组件、composables、types、styles、stores） |
| `@mdm/config-vite` | **packages/config-vite** | Vite 构建预设（AutoImport、Components 插件、路径别名） |

## 4. 关键设计决策

### 4.1 类型分层：基础类型在 core 中定义

`core/http` 的 Axios 拦截器需要引用 `ApiResponse` 类型。为保证 `@mdm/core` 完全自包含、不依赖 `@mdm/common`，将基础 API 类型和实体类型定义在 `@mdm/core` 中：

```
@mdm/core：
  src/types/api.ts          # ApiResponse<T>, PaginatedResponse<T>, IdParam
  src/types/base.ts         # ID, BaseEntity, AuditInfo, PaginationParams, PaginatedData
  src/types/index.ts        # 统一导出

@mdm/common：
  src/types/base.ts         # 从 @mdm/core 重新导出（便于业务代码就近引入）
  src/types/api.ts          # 从 @mdm/core 重新导出
  src/types/tree.ts         # TreeNode, TreeSelectOption, LazyTreeNode（依赖 @mdm/core 的 ID）
  src/types/import-export.ts # ImportTaskEntity, ExportParams（依赖 @mdm/core 的 ID）
```

`@mdm/core` 完全自包含，不依赖 `@mdm/common`。`@mdm/common` 中的 `types/base.ts` 和 `types/api.ts` 通过 re-export 提供兼容入口，业务代码可从任意一处导入。

### 4.2 路由：工厂函数 + app 层 glob 扫描

Monorepo 中 `modules/` 目录位于 app 层而非共享包中，而 `import.meta.glob` 是 Vite 编译时特性，默认不扫描 `node_modules`（包括 pnpm workspace 的 symlinked 包）。因此路由采用工厂函数模式：

`@mdm/core` 提供工厂函数：

```ts
// packages/mdm-core/src/router/index.ts
import { createRouter, createWebHashHistory } from 'vue-router';
import type { RouteRecordRaw } from 'vue-router';

export interface CreateRouterOptions {
  /** 基础路由（如 / → /model-design 的重定向） */
  baseRoutes?: RouteRecordRaw[];
}

export function createAppRouter(
  moduleRoutes: RouteRecordRaw[],
  options: CreateRouterOptions = {},
) {
  const { baseRoutes = [] } = options;
  
  const router = createRouter({
    history: createWebHashHistory(),
    routes: [...baseRoutes, ...moduleRoutes],
  });

  router.beforeEach((to, _from, next) => {
    const title = to.meta.title as string;
    if (title) {
      document.title = `${title} - ${import.meta.env.VITE_APP_TITLE ?? '主数据管理平台'}`;
    }
    next();
  });

  return router;
}
```

各 app 在自己的 `router.ts` 中使用 `import.meta.glob` 扫描本地模块并组装：

```ts
// apps/mdm-model/src/router.ts
import { createAppRouter } from '@mdm/core/router';
import type { RouteRecordRaw } from 'vue-router';

const moduleFiles = import.meta.glob<{ default: RouteRecordRaw[] }>(
  ['./modules/*/routes.ts', '!./modules/_*/routes.ts'],
  { eager: true },
);

const moduleRoutes: RouteRecordRaw[] = Object.values(moduleFiles)
  .flatMap((m) => m.default ?? []);

const router = createAppRouter(moduleRoutes, {
  baseRoutes: [{ path: '/', redirect: '/model-design' }],
});

export default router;
```

`import.meta.glob` 在 Vite 编译时解析，路径相对于 app 的 `src/` 目录，能正确扫描 `apps/mdm-model/src/modules/` 下的文件。

### 4.3 i18n：工厂函数 + app 层 glob 扫描

与路由同理，`@mdm/core` 提供 `createAppI18n()` 工厂函数，app 层负责扫描本地语言包：

```ts
// packages/mdm-core/src/i18n/index.ts
import { createI18n } from 'vue-i18n';

export interface I18nModuleEntry {
  /** camelCase 模块名，如 modelDesign */
  name: string;
  /** zh-CN 语言包 */
  zhCN: Record<string, unknown>;
  /** en-US 语言包 */
  enUS: Record<string, unknown>;
}

export function createAppI18n(
  modules: I18nModuleEntry[],
  commonLocales: { zhCN: Record<string, unknown>; enUS: Record<string, unknown> },
) {
  const zhMessages: Record<string, unknown> = { common: commonLocales.zhCN };
  const enMessages: Record<string, unknown> = { common: commonLocales.enUS };

  for (const mod of modules) {
    zhMessages[mod.name] = mod.zhCN;
    enMessages[mod.name] = mod.enUS;
  }

  return createI18n({
    legacy: false,
    locale: 'zh-CN',
    fallbackLocale: 'zh-CN',
    messages: { 'zh-CN': zhMessages, 'en-US': enMessages },
  });
}
```

### 4.4 Vite 配置共享

`@mdm/config-vite` 提供工厂函数，各 app 的 `vite.config.ts` 在此基础上补充本地配置：

```ts
// packages/config-vite/src/index.ts
import vue from '@vitejs/plugin-vue';
import AutoImport from 'unplugin-auto-import/vite';
import Components from 'unplugin-vue-components/vite';
import { ElementPlusResolver } from 'unplugin-vue-components/resolvers';
import type { UserConfig } from 'vite';
import path from 'node:path';

export interface MdmViteOptions {
  /** app 根目录（通常是 import.meta.url 对应目录） */
  root: string;
  /** 是否启用 mock 插件 */
  useMock?: boolean;
  /** mock 插件实例（由 app 自行创建并传入） */
  mockPlugin?: any;
  /** 额外的组件扫描目录 */
  extraComponentDirs?: string[];
  /** 开发服务器端口，默认 3000 */
  port?: number;
}

export function createMdmViteConfig(options: MdmViteOptions): UserConfig {
  const { root, useMock, mockPlugin, extraComponentDirs = [], port = 3000 } = options;

  return {
    plugins: [
      vue(),
      AutoImport({
        resolvers: [ElementPlusResolver()],
        imports: ['vue', 'vue-router', 'pinia', 'vue-i18n'],
        dts: path.resolve(root, 'src/auto-imports.d.ts'),
      }),
      Components({
        resolvers: [ElementPlusResolver()],
        dirs: [
          path.resolve(root, 'src/components'),
          ...extraComponentDirs,
        ],
        dts: path.resolve(root, 'src/components.d.ts'),
      }),
      useMock && mockPlugin,
    ].filter(Boolean),
    resolve: {
      alias: {
        '@': path.resolve(root, 'src'),
      },
    },
    server: {
      port,
      // 允许 Vite dev server 访问 monorepo 根目录下的共享包源码
      fs: {
        allow: [path.resolve(root, '../..')],
      },
    },
    // 确保内部包被正确预构建
    optimizeDeps: {
      include: ['@mdm/core', '@mdm/common'],
    },
  };
}
```

```ts
// apps/mdm-model/vite.config.ts
import { defineConfig, loadEnv } from 'vite';
import { createMdmViteConfig } from '@mdm/config-vite';
import { mockPlugin } from './mock/vite-plugin-mock';
import path from 'node:path';

export default defineConfig(({ mode }) => {
  const env = loadEnv(mode, process.cwd(), '');
  const useMock = env.VITE_USE_MOCK === 'true';

  const base = createMdmViteConfig({
    root: __dirname,
    useMock,
    mockPlugin: mockPlugin(),
    port: 3000,
  });

  return {
    ...base,
    server: {
      ...base.server,
      ...(useMock ? {} : {
        proxy: {
          '/api': {
            target: env.VITE_API_BASE_URL || 'http://localhost:8080',
            changeOrigin: true,
          },
        },
      }),
    },
  };
});
```

### 4.6 Store 架构模式：页面层持有，子组件消费

Store 使用不当会引入层间耦合。一旦深层子组件直接引用 store，该组件就和特定数据源绑死，无法复用、难以测试。为此采用"容器/展示"分层：

**业务 store 的使用权收敛到页面级组件**（`views/` 下的 `*List.vue`、`*Detail.vue`、`*Editor.vue`），子组件（`components/` 下的面板、弹窗、抽屉等）通过 props 接收数据、emits 回传操作意图，不直接引用业务 store。

```
页面级组件（容器）                       子组件（展示）
┌──────────────────────────┐          ┌──────────────────────────┐
│  ModelDetail.vue          │          │  AttributePanel.vue       │
│                           │          │                           │
│  const store =            │  props   │  defineProps<{            │
│    useModelStore()        │────────▶│    attributes: Attr[]     │
│                           │          │    loading: boolean       │
│  handleSave() {           │  emits   │  }>()                     │
│    store.saveAttribute()  │◀────────│  emit('save', data)       │
│  }                        │          │                           │
└──────────────────────────┘          └──────────────────────────┘
```

层级超过 2 层时（如 DetailPage → Tab → Section → Field），中间组件仅做 props 中转会导致透传层级过深、维护困难，可在页面级组件中通过 `provide` 注入数据，深层子组件通过 `inject` 消费，但 provide 的注入点必须在页面级组件的 `setup` 中。

全局 UI store（`useAppStore`：locale、sidebar、permissions）属于跨页面共享状态，不受此约束，可在任意组件中直接引用。

完整的 Store 使用规范（R1-R5 规则明细、定义规范、放置位置）见 `docs/rules/coding-rules.md` 第 4 节。

### 4.7 平台配置体系：字体 / 换肤 / 国际化

字体切换、换肤、国际化三项全局 UI 能力统一由 `@mdm/core/config` 模块管理。

**当前阶段**：配置参数的获取方式尚未确定（接口、静态文件、平台 SDK 等均有可能），项目先使用**框架内置的固定值**运行。

**设计策略**：将"配置长什么样"（数据结构）与"配置从哪来"（获取方式）解耦。配置结构通过 `PlatformConfig` 类型定义固定下来，获取方式通过策略模式抽象，后续确定来源时只需替换 provider 实现，不改应用层逻辑。

#### 4.7.1 配置来源与获取方式

配置参数的获取方式尚未最终确定，可能的方案包括：

| 方案 | 说明 | 适用场景 |
|---|---|---|
| 框架固定值 | 前端内置默认配置，无需外部获取 | 当前阶段 |
| REST API | 后端接口返回配置（如 `GET /api/v1/platform/config`） | 平台统一管理配置 |
| 静态配置文件 | 项目中的 JSON/YAML 文件，构建时注入 | 配置变化不频繁 |
| 平台 SDK | 调用平台提供的 JS SDK 获取配置 | 平台有现成 SDK |

**当前实现**：使用框架固定值。获取方式确定后，只需新增对应的 `ConfigProvider` 实现并注册，应用层代码无需修改。

#### 4.7.2 配置数据结构

无论配置从何处获取，前端统一使用 `PlatformConfig` 类型描述：

```ts
interface PlatformConfig {
  theme: ThemeConfig;       // 换肤
  font: FontConfig;         // 字体
  i18n: I18nConfig;         // 国际化
  appTitle?: string;
}

interface ThemeConfig {
  primaryColor: string;    // 主色，如 '#409EFF'
  backgroundColor: string; // 背景色，如 '#FFFFFF'
  darkMode?: boolean;      // 暗色模式（预留）
}

interface FontConfig {
  fontSize: number;        // px
}

interface I18nConfig {
  locale: string;          // 默认语言，如 'zh-CN'
  availableLocales: string[];
  fallbackLocale: string;  // 回退语言
}
```

该结构与获取方式解耦——API 返回、静态文件、SDK 回调最终都转换为 `PlatformConfig` 对象传入应用层。

#### 4.7.3 框架固定值（当前配置来源）

当前阶段所有配置项使用框架内置的固定值，作为项目运行时的唯一配置来源：

采用策略模式，将"获取配置"抽象为 `ConfigProvider`，当前使用 `StaticProvider`（返回固定值），后续确定来源后替换：

    │

// @mdm/core/config/loader.ts
import type { ConfigProvider, PlatformConfig } from './types';
import { DEFAULT_CONFIG } from './defaults';
import { applyConfig } from './apply';
import { deepMerge } from './utils';

export async function loadAndApplyConfig(provider: ConfigProvider): Promise<PlatformConfig> {
  let config: PlatformConfig = { ...DEFAULT_CONFIG };

  try {
    const external = await provider.load();
    config = deepMerge(DEFAULT_CONFIG, external);
  } catch {
    console.warn('[config] 配置获取失败，使用框架固定值');

  applyConfig(config);
  return config;
}

#### 4.7.8 `useAppStore` 改造

```ts
// @mdm/common/stores/useAppStore.ts
import { defineStore } from 'pinia';
import type { PlatformConfig } from '@mdm/core/config/types';
import { applyConfig } from '@mdm/core/config/apply';

export const useAppStore = defineStore('app', () => {
  const config = ref<PlatformConfig | null>(null);
  const locale = ref('zh-CN');
  const sidebarCollapsed = ref(false);
  const permissions = ref<string[]>([]);

  /** main.ts 中配置加载完成后调用 */
  function init(resolvedConfig: PlatformConfig) {
    config.value = resolvedConfig;
    locale.value = resolvedConfig.i18n.locale;
  }

  /** 切换语言 — 当前为项目内切换，平台方案确定后对接平台 locale */
  function setLocale(newLocale: string) {
    locale.value = newLocale;
    // i18n.global.locale 由 i18n 模块内部监听 locale 同步
  }

  /** 切换主色 — 运行时修改 CSS 变量 */
  function setPrimaryColor(color: string) {
    if (!config.value) return;
    config.value.theme.primaryColor = color;
    applyConfig(config.value);
  }

  function hasPermission(p: string) {
    return permissions.value.includes(p);
  }

  return {
    config, locale, sidebarCollapsed, permissions,
    init, setLocale, setPrimaryColor, hasPermission,
  };
});
```

#### 4.7.11 Element Plus 换肤方案

Element Plus 通过 CSS 变量实现运行时换肤，所有组件的颜色、圆角、阴影等均由 CSS 变量驱动。项目换肤的核心思路是：**在运行时修改 `:root` 上的 Element Plus CSS 变量，组件自动响应变化，无需重新编译。**

**Element Plus 主色变量体系**

Element Plus 以 `--el-color-primary` 为基准色，自动派生出不同明度的色阶变量，用于按钮 hover/active、标签背景、输入框 focus 边框等场景：

| CSS 变量 | 说明 | 示例（主色 #409EFF） |
|---|---|---|
| `--el-color-primary` | 基准主色 | `#409EFF` |
| `--el-color-primary-light-3` | 混合 30% 白色 | `#79bbff` |
| `--el-color-primary-light-5` | 混合 50% 白色 | `#a0cfff` |
| `--el-color-primary-light-7` | 混合 70% 白色 | `#c6e2ff` |
| `--el-color-primary-light-8` | 混合 80% 白色 | `#d9ecff` |
| `--el-color-primary-light-9` | 混合 90% 白色 | `#ecf5ff` |
| `--el-color-primary-dark-2` | 混合 20% 黑色 | `#337ecc` |

同理，`success`、`warning`、`danger`、`info` 也各有对应的色阶变量。

**`generateColorVariants` 实现**

通过 `mix` 函数将主色与白色/黑色按比例混合，生成完整色阶并写入 CSS 变量：

```ts
// @mdm/core/config/utils.ts

/** 将两个颜色按百分比混合（hex → rgb → mix → hex） */
function mix(color1: string, color2: string, weight: number): string {
  const d = (hex: string) => parseInt(hex.slice(1), 16);
  const c1 = d(color1), c2 = d(color2);
  const w = weight / 100;
  const r = Math.round(((c1 >> 16) & 0xff) * w + ((c2 >> 16) & 0xff) * (1 - w));
  const g = Math.round(((c1 >> 8) & 0xff) * w + ((c2 >> 8) & 0xff) * (1 - w));
  const b = Math.round((c1 & 0xff) * w + (c2 & 0xff) * (1 - w));
  return `#${((r << 16) | (g << 8) | b).toString(16).padStart(6, '0')}`;
}

/** 根据主色生成 Element Plus 所需的色阶变量 */
export function generateColorVariants(primaryColor: string) {
  const root = document.documentElement;
  const lightSteps = [3, 5, 7, 8, 9];
  for (const step of lightSteps) {
    root.style.setProperty(
      `--el-color-primary-light-${step}`,
      mix(primaryColor, '#ffffff', 1 - step / 10)
    );
  }
  root.style.setProperty(
    '--el-color-primary-dark-2',
    mix(primaryColor, '#000000', 0.8)
  );
}
```

**换肤生效链路**

```
用户/平台设置主色 #1677FF
       │
       ▼
applyConfig() 写入 --el-color-primary: #1677FF
       │
       ▼
generateColorVariants() 写入 --el-color-primary-light-* / dark-*
       │
       ▼
Element Plus 组件自动读取 CSS 变量 → 按钮、输入框、标签等全部变色
       │
       ▼
Tailwind 的 colors.primary 引用 var(--el-color-primary) → 自定义组件同步变色
```

这样，只需修改一个 `primaryColor` 值，整个应用的主题色（包括 Element Plus 组件和 Tailwind 自定义组件）就会同步切换，无需逐个组件覆盖样式。

**CSS 变量**

|---|---|---|
| `--mdm-font-size` | 全局基础字号 | `12px` |

**生效链路**

#### 4.7.13 国际化方案

国际化基于 `vue-i18n`，采用**工厂函数 + app 层 glob 扫描**的模式，分为三层语言包：

```
┌─────────────────────────────────────────────┐
│  第 1 层：@mdm/common/locales/               │
│  zh-CN.ts / en-US.ts                        │
│  → 共享组件的通用文案（common.*）              │
├─────────────────────────────────────────────┤
│  第 2 层：apps/*/src/modules/*/locales/       │
│  zh-CN.ts / en-US.ts                        │
│  → 各业务模块的专属文案                        │
├─────────────────────────────────────────────┤
│  第 3 层：Element Plus 内置 locale            │
│  element-plus/es/locale/lang/zh-cn          │
│  → Element Plus 组件自身的翻译                 │
└─────────────────────────────────────────────┘
```

**i18n 消息结构**

运行时合并后的 messages 结构：

```ts
{
  'zh-CN': {
    common: { /* @mdm/common 的通用文案 */ },
    modelDesign: { /* 主数据建模模块文案 */ },
    metamanageData: { /* 数据项模块文案 */ },
    // ...
  },
  'en-US': { /* 同上 */ }
}
```

**`createAppI18n` 工厂函数**

```ts
// @mdm/core/i18n/index.ts
export function createAppI18n(
  modules: I18nModuleEntry[],
  commonLocales: { zhCN: Record<string, unknown>; enUS: Record<string, unknown> },
) {
  const zhMessages = { common: commonLocales.zhCN };
  const enMessages = { common: commonLocales.enUS };

  for (const mod of modules) {
    zhMessages[mod.name] = mod.zhCN;
    enMessages[mod.name] = mod.enUS;
  }

  return createI18n({
    legacy: false,
    locale: 'zh-CN',
    fallbackLocale: 'zh-CN',
    messages: { 'zh-CN': zhMessages, 'en-US': enMessages },
  });
}
```

**app 层组装**

各 app 在 `i18n.ts` 中扫描本地模块语言包，与共享层合并后传入工厂函数：

```ts
// apps/mdm-model/src/i18n.ts
import { createAppI18n } from '@mdm/core/i18n';
import zhCommon from '@mdm/common/locales/zh-CN';
import enCommon from '@mdm/common/locales/en-US';

// glob 扫描本 app 各模块的语言包
const zhModules = import.meta.glob('./modules/*/locales/zh-CN.ts', { eager: true });
const enModules = import.meta.glob('./modules/*/locales/en-US.ts', { eager: true });

// 组装为 I18nModuleEntry[] 并调用 createAppI18n()
```

**Element Plus locale 同步**

Element Plus 组件（日期选择器、分页等）有自己独立的 locale 对象。切换语言时需同步更新：

```ts
// main.ts 中根据当前 locale 动态导入
const epLocale = config.i18n.locale.startsWith('zh')
  ? (await import('element-plus/es/locale/lang/zh-cn')).default
  : (await import('element-plus/es/locale/lang/en')).default;

```

**运行时切换语言**

### 4.8 多路径跳转

### 4.9 Auth 模块

`@mdm/core/auth` 负责 token 的存取与登录状态判断。

**存储方式**：token 存储在 `localStorage` 中，key 固定为 `mdm_token`。

```ts
// @mdm/core/auth/index.ts
const TOKEN_KEY = 'mdm_token';

export function getToken(): string | null {
  return localStorage.getItem(TOKEN_KEY);
}

export function setToken(token: string): void {
  localStorage.setItem(TOKEN_KEY, token);
}

export function removeToken(): void {
  localStorage.removeItem(TOKEN_KEY);
}

export function isLoggedIn(): boolean {
  return !!getToken();
}

export function logout(): void {
  removeToken();
  window.location.hash = '#/login'; // 跳转登录页
}
```

http 模块的请求拦截器通过 `getToken()` 自动注入 `Authorization: Bearer <token>` 请求头。响应拦截器在收到 401 时调用 `logout()`。

### 4.10 HTTP 模块

`@mdm/core/http` 提供全局 Axios 实例及拦截器。

**请求拦截器**：

- 自动注入 `Authorization: Bearer <token>`（从 `@mdm/core/auth` 读取）
- 统一设置 `Content-Type: application/json`

**响应拦截器**：

- 解包 `ApiResponse<T>` 结构，将 `res.data.data` 传递给业务代码
- 统一错误处理：HTTP 401 → 调用 `logout()`；其他错误 → `ElMessage.error` 提示
- 网络异常（超时、断网）→ 统一 toast 提示

```ts
// @mdm/core/http/index.ts
import axios from 'axios';
import { getToken, logout } from '../auth';

const http = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || '',
  timeout: 30000,
});

http.interceptors.request.use((config) => {
  const token = getToken();
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

http.interceptors.response.use(
  (response) => {
    const data = response.data;
    if (!data.success) {
      // 业务错误
      console.error('[http]', data.message);
      return Promise.reject(new Error(data.message || '请求失败'));
    }
    return response;
  },
  (error) => {
    if (error.response?.status === 401) {
      logout();
    }
    return Promise.reject(error);
  },
);

export { http };
```

## 7. Turborepo 任务流

### 7.1 `turbo run build`（全量构建）

```
@mdm/config-vite#build ──────────────────────────────┐
                                                      │
@mdm/core#build ──────────────────┐                   │
                                  ▼                   │
@mdm/common#build ───────────────►│                   │
                                  ▼                   │
@mdm/flow-app#build ◄─────────────┤                   │
                                  │                   │
@mdm/metamanage-app#build ◄───────┘                   │
                                                      │
                                     (缓存命中则跳过) │
```

Turborepo 根据 `dependsOn: ["^build"]` 自动编排依赖顺序。由于 `@mdm/core` 和 `@mdm/common` 以源码形式直接引用（`main: "./src/index.ts"`），它们的 `build` 任务实际上是类型检查（`vue-tsc --noEmit`），不产出 dist 产物。

### 7.2 `turbo run dev`（开发模式）

开发模式下，Vite 的 HMR 直接通过 pnpm workspace 的符号链接解析共享包的源码。修改 `packages/mdm-common/src/components/data/TpTable.vue` 后，两个 app 的开发服务器都能触发热更新。

`@mdm/core` 和 `@mdm/common` 不需要自己的 dev server——它们是纯源码包，由 app 的 Vite 直接编译。

### 7.3 缓存策略

```json
{
  "tasks": {
    "build": {
      "outputs": ["dist/**"],
      "inputs": ["src/**", "index.html", "vite.config.ts", "tsconfig.json"]
    },
    "typecheck": {
      "outputs": [],
      "inputs": ["src/**", "tsconfig.json"]
    }
  }
}
```

当 `@mdm/core` 的源码未变化时，`turbo run typecheck` 会命中缓存直接跳过，避免重复执行同一检查。

### 9.2 各目录职责

#### `rules/` — 项目规则

存放所有约束性文档，定义"怎么做"和"不能怎么做"。这些文件是 AI 编码助手和人类开发者在写代码前必读的基线。

**`coding-rules.md`** 覆盖命名规则（页面后缀、组件 name、路由名、API 函数名）、`<script setup>` 块顺序（10 项硬约束）、跨层依赖禁令、`any` 禁用规则等。这是从前端工程结构文档中抽取并扩充的纯规范文件。

**`monorepo-conventions.md`** 覆盖包间依赖硬约束（第 3.2 节）、`import.meta.glob` 只能在 app 层使用的约束、`peerDependencies` 声明规范、共享包 `build` 脚本要求、`server.fs.allow` 配置要求等。

**`ai-coding-rules.md`** 是 AI 辅助编码的专属入口文件。汇总 AI 写代码前必须遵守的所有硬约束（引用 `coding-rules.md` 和 `monorepo-conventions.md` 的关键条款），并附加 AI 专属约定（如禁止执行 `npm test`、改动 CSS/页面结构时须用 chrome-devtools-mcp 点测等）。根目录的 `CLAUDE.md` 和 `AGENTS.md` 作为各 AI 工具的入口文件保持精简，指向此文档获取完整规则。

**`git-workflow.md`** 定义分支策略（如 Git Flow 或 Trunk-Based）、commit message 格式（如 Conventional Commits）、PR 流程、代码评审要求等。

#### `architecture/` — 架构设计

存放描述"系统长什么样"的结构性文档。

**`monorepo-design.md`** 就是本文档，描述 Monorepo 的整体架构、技术选型、包划分、依赖关系、配置详解、构建流程等。

**`engineering-structure.md`** 是面向日常开发的技术参考手册，包含技术栈清单、目录结构、三层架构说明、自动发现机制、业务模块清单（含子模块概览）、路由清单、公共组件/composables 清单、HTTP 响应约定、i18n 结构、Mock 数据清单等。开发者在编写业务代码时可直接查阅这份文档。

#### `requirements/` — 需求文档

存放产品需求说明书（PRD），描述"做什么"。按业务模块拆分，每份文档对应一个独立的功能域。支持 `.md` 和 `.docx` 两种格式，`.docx` 放在同目录下，`.md` 作为提取后的可读版本。

#### `modules/` — 模块设计文档

存放模块级的技术设计文档，描述"具体怎么实现"。与 `apps/*/src/modules/` 中的业务模块一一对应。

与 `docs/` 下其他一级目录不同，`modules/` 采用**按模块分文件夹**的方式组织，每个模块文件夹下包含：

| 文件 | 职责 |
|---|---|
| `README.md` | 模块索引（概述、对应源码路径、关联需求文档） |
| `design.md` | 设计文档（实体模型、状态机、页面/组件设计、路由、composables、store） |
| `api.md` | 模块 API 契约（接口列表、请求参数、响应示例） |

`requirements/` 和 `modules/` 的区别：需求文档描述业务规则和用户场景（"数据项支持按分组分类、按类型筛选"），模块设计文档描述技术实现方案（"使用 TpLeftTreeLayout 实现左树右表布局，useCrudList 管理分页状态"）。

#### `api/` — API 全局约定

存放 API 全局约定文档，不包含模块级接口细节。

**`overview.md`** 定义全局约定：响应格式（`ApiResponse<T>`、`PaginatedResponse<T>`）、API 函数命名 5 件套（list/get/create/update/delete）、错误码枚举、认证方式（Bearer token）、路径前缀规范（`/api/v1/{module}/{entity}`）等。

各模块的具体接口文档统一收归到 `modules/{module-name}/api.md` 中维护，与模块设计文档同目录，便于同步更新。

### 9.3 `README.md` 索引规范

`docs/README.md` 作为整个文档目录的入口，应包含：

- 目录结构的快速导航（带链接指向各文件）。
- 文档编写规范：文件命名规则（kebab-case 英文或中文短名）、文档头部模板（标题、最后更新日期、关联模块）、Markdown 格式约定。
- 文档更新责任：修改业务模块代码时须同步更新对应的 `modules/{name}/design.md`；新增 API 须同步更新 `modules/{name}/api.md`；修改编码规范须同步更新 `rules/*.md`。

### 9.4 根目录入口文件

仓库根目录保留少量入口文件，指向 `docs/` 中的详细文档：

| 文件 | 职责 |
| --- | --- |
| `CLAUDE.md` | Claude Code 入口，精简列出关键命令和规则引用，指向 `docs/rules/ai-coding-rules.md` |

根目录不应再放置其他 `.md` 文档文件，所有项目文档统一收归 `docs/` 管理。

### 10.3 `useModuleMenu(route)` 约定

AppLayout 通过 `useModuleMenu(route)` 从当前激活路由动态生成侧边栏菜单。

```ts
// packages/mdm-core/src/router/index.ts
export function useModuleMenu(route) {
  // 找到第一个 meta.menu === true 的父级路由（模块根）
  const parent = route.matched.find((r) => r.meta?.menu === true);
  const children = parent?.children ?? [];
  return children
    .filter((c) => c.meta?.menu !== false && c.meta?.hidden !== true)
    .map((c) => ({
      name: c.name,
      path: c.path,
      title: c.meta?.title,
      icon: c.meta?.icon,
      order: c.meta?.order ?? 0,
    }))
    .sort((a, b) => a.order - b.order);
}
```

**模块 routes 约定**：

```ts
{
  path: `/${MODULE_NAME}`,
  component: Layout,
  meta: { title, icon, menu: true, order },  // 父级：标记为菜单根
  children: [
    {
      path: '',
      name: `${MODULE_NAME}-list`,
      component: () => import('./views/...'),
      meta: { title, icon, menu: true, order: 1, permission: `${MODULE_NAME}:read` },
    },
    {
      path: ':id',
      name: `${MODULE_NAME}-detail`,
      component: () => import('./views/...'),
      meta: { title, menu: false, hidden: true, permission: `${MODULE_NAME}:read` },  // 隐藏路由
    },
  ],
}
```
